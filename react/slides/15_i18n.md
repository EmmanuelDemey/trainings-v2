# 15 - Internationalisation

---

# Learning objectives

At the end of this chapter, you will be able to:

- **Distinguish** the two halves of i18n: **formatting** values (numbers, dates, units)
  and **translating** messages
- **Format** numbers, units, dates and relative times with the native `Intl` API —
  no library
- **Set up** i18next and react-i18next, **translate** with `useTranslation`, and
  **switch** the language at runtime
- **Interpolate** values and **pluralise** messages with `count` — and know when ICU
  syntax is worth it
- **Type** the translation keys so that a typo is a compile error

---

# Internationalisation, in two halves

<br />

| | Example | Tool |
|---|---|---|
| **Formatting** | `1,234.5` vs `1 234,5` · `12/20/2026` vs `20/12/2026` · `172 cm` | `Intl` (built in) |
| **Translating** | "Welcome" vs "Bienvenue" · "1 person" vs "2 people" | i18next + react-i18next |

<br />

- **i18n** = internationalisation (making the app *able* to adapt), **l10n** = localisation
  (the actual French, German… versions)
- A **locale** is a BCP 47 tag: `en`, `en-GB`, `fr-FR`, `pt-BR`
- Never concatenate translated fragments: word order changes between languages

---

# `Intl.NumberFormat`

```ts
const n = 123456.789;

new Intl.NumberFormat('en-US').format(n);   // "123,456.789"
new Intl.NumberFormat('fr-FR').format(n);   // "123 456,789"

new Intl.NumberFormat('de-DE', { style: 'currency', currency: 'EUR' }).format(n);
// "123.456,79 €"

new Intl.NumberFormat('en', { style: 'unit', unit: 'centimeter' }).format(172);
// "172 cm"
new Intl.NumberFormat('fr', { style: 'unit', unit: 'kilogram', unitDisplay: 'long' }).format(77);
// "77 kilogrammes"

new Intl.NumberFormat('en', { notation: 'compact' }).format(1_200_000);   // "1.2M"
new Intl.NumberFormat('en', { style: 'percent' }).format(0.256);           // "26%"
```

- Create the formatter **once** and reuse it: construction is the expensive part

---

# `Intl.DateTimeFormat`

```ts
const date = new Date(Date.UTC(2026, 11, 20, 3, 0, 0));

new Intl.DateTimeFormat('en-US').format(date);              // "12/20/2026"
new Intl.DateTimeFormat('fr-FR').format(date);              // "20/12/2026"

new Intl.DateTimeFormat('en-GB', { dateStyle: 'full' }).format(date);
// "Sunday, 20 December 2026"

new Intl.DateTimeFormat('fr', { dateStyle: 'medium', timeStyle: 'short', timeZone: 'Europe/Paris' })
  .format(date);                                            // "20 déc. 2026, 04:00"
```

- `dateStyle` / `timeStyle`: `'full' | 'long' | 'medium' | 'short'` — the locale decides the rest
- Always think about the **time zone**: the default is the user's

# Relative time and plural rules

```ts
const rtf = new Intl.RelativeTimeFormat('en', { numeric: 'auto' });
rtf.format(-1, 'day');      // "yesterday"
rtf.format(-3, 'day');      // "3 days ago"
rtf.format(2, 'week');      // "in 2 weeks"

new Intl.RelativeTimeFormat('fr', { numeric: 'auto' }).format(-1, 'day');   // "hier"
new Intl.RelativeTimeFormat('fr').format(-3, 'day');                        // "il y a 3 jours"
```

```ts
const rules = new Intl.PluralRules('en');
rules.select(1);   // "one"
rules.select(2);   // "other"

new Intl.PluralRules('fr').select(0);     // "one"  — 0 is singular in French
new Intl.PluralRules('pl').select(5);     // "many" — Polish has 4 categories
```

- `PluralRules` is what i18next uses under the hood to choose a plural form
- Also built in: `Intl.ListFormat` ("Luke, Leia, and Han"), `Intl.Collator` (sorting with accents)

---

# Dates: do you need a library?

- `Intl` **formats** — it doesn't add days, parse strings or compute differences
- For date arithmetic:
  - **Temporal** — the new built-in date API (`Temporal.PlainDate`, `Temporal.Duration`),
    shipping in browsers; a polyfill exists for the others
  - **date-fns** — small pure functions, tree-shakable
  - **Day.js** — tiny, Moment-like API
  - ~~Moment~~ — in maintenance mode, large and mutable: don't start with it

<br />

```ts
import { differenceInYears } from 'date-fns';

const age = differenceInYears(new Date(), person.birthDate);
```

# Translating with i18next

- **i18next** — the translation engine: dictionaries, fallbacks, plurals, interpolation,
  formatting, plugins (HTTP backend, language detection, ICU)
- **react-i18next** — the React binding: `useTranslation`, `<Trans>`, re-render on
  language change

```shell
npm install i18next react-i18next
```

```ts
// src/i18n/en.ts — one object per language
export const en = {
  title: 'Star Wars people',
  welcome: 'Welcome, {{name}}!',
  people_zero: 'No one found',
  people_one: '{{count}} person',
  people_other: '{{count}} people',
} as const;   // literal types: lets TypeScript check the {{variables}} (see "Typed keys")
```

# Configuration

```ts
// src/i18n/index.ts
import i18n from 'i18next';
import { initReactI18next } from 'react-i18next';
import { en } from './en';
import { fr } from './fr';

export const resources = {
  en: { translation: en },
  fr: { translation: fr },
} as const;

i18n.use(initReactI18next).init({
  resources,
  lng: 'en',                         // initial language (or a language detector plugin)
  fallbackLng: 'en',                 // a key missing in fr falls back to en
  interpolation: { escapeValue: false },   // React already escapes what it renders
});

export default i18n;
```

```ts
// main.tsx — import it once, before rendering
import './i18n';
```

# `useTranslation`

```tsx
import { useTranslation } from 'react-i18next';

function Header({ user }: { user: string }) {
  const { t } = useTranslation();

  return (
    <header>
      <h1>{t('title')}</h1>
      <p>{t('welcome', { name: user })}</p>       {/* "Welcome, Luke!" */}
    </header>
  );
}
```

- The component **re-renders** when the language changes
- With resources inline, the translations are ready synchronously — no `Suspense` needed
- With an HTTP backend (`i18next-http-backend`), `useTranslation` **suspends** until the
  namespace is loaded: wrap the app in `<Suspense>`

---

# Switching the language

```tsx
function LanguageSwitcher() {
  const { t, i18n } = useTranslation();

  return (
    <label>
      {t('language')}
      <select value={i18n.resolvedLanguage} onChange={(e) => i18n.changeLanguage(e.target.value)}>
        <option value="en">English</option>
        <option value="fr">Français</option>
      </select>
    </label>
  );
}
```

```ts
i18n.on('languageChanged', (lng) => {
  document.documentElement.lang = lng;        // screen readers, hyphenation, spell check
});
```

- `resolvedLanguage`: the language actually used (`'en'` even when the browser said `'en-GB'`)
- `i18next-browser-languagedetector` picks it from the browser / `localStorage`

# Plurals

```ts
// en                                         // fr
people_zero: 'No one found',                  people_zero: 'Personne',
people_one: '{{count}} person',               people_one: '{{count}} personne',
people_other: '{{count}} people',             people_other: '{{count}} personnes',
```

```tsx
t('people', { count: 0 });   // "No one found" / "Personne"
t('people', { count: 1 });   // "1 person"     / "1 personne"
t('people', { count: 3 });   // "3 people"     / "3 personnes"
```

- The variable **must** be named `count`; i18next picks the suffix with `Intl.PluralRules`
  (`_one`, `_few`, `_many`, `_other`…) — each language has its own set
- `_zero` is an i18next extra for a special "nothing" message
- Never write `count > 1 ? … : …`: it's wrong in French (0) and in most languages

---

# Formatting inside messages

i18next formats interpolated values with `Intl`, using the current language:

```ts
height: 'Height: {{value, number(maximumFractionDigits: 1)}} m',
updated: 'Updated {{when, relativetime(day)}}',
born: 'Born on {{date, datetime(dateStyle: long)}}',
```

```tsx
t('height', { value: 1.72 });          // "Height: 1.7 m"    / "Taille : 1,7 m"
t('updated', { when: -3 });            // "Updated 3 days ago"
t('born', { date: new Date(1977, 4, 25) });
```

- Built-in formats: `number`, `currency`, `datetime`, `relativetime`, `list`
- Or format in the component with `Intl.*Format(i18n.resolvedLanguage)` and pass a string

# Markup in translations: `<Trans>`

```ts
terms: 'I accept the <link>terms of use</link>.',
```

```tsx
import { Trans } from 'react-i18next';

<Trans i18nKey="terms" components={{ link: <a href="/terms" /> }} />
// <>I accept the <a href="/terms">terms of use</a>.</>
```

- Translators move `<link>` wherever the language needs it
- Never put HTML in a message and render it with `dangerouslySetInnerHTML`

# ICU MessageFormat — optional

A standard syntax (also used by FormatJS / react-intl), via the `i18next-icu` plugin:

```shell
npm install i18next-icu
```

```ts
import ICU from 'i18next-icu';
i18n.use(ICU).use(initReactI18next).init({ /* … */ });
```

```ts
friends: '{count, plural, =0 {no friend} one {one friend} other {# friends}}',
greeting: '{gender, select, female {She} male {He} other {They}} liked your post',
```

- One key holds every variant: translation tools and translators often prefer it
- Pick **one** syntax per project: native i18next suffixes or ICU, not both

# Typed translation keys

```ts
// src/i18n/i18next.d.ts
import 'i18next';
import type { en } from './en';

declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'translation';
    resources: { translation: typeof en };
  }
}
```

```ts
// src/i18n/fr.ts — every language must have the same keys
import type { en } from './en';

export const fr = {
  title: 'Personnages de Star Wars',
  welcome: 'Bienvenue, {{name}} !',  /* … */
} satisfies Record<keyof typeof en, string>;
```

```tsx
t('titel');                      // ❌ compile error: not a key
t('welcome', { nmae: 'Luke' });  // ❌ compile error: property 'name' is missing
```

- `en` is the **source of truth** (`as const`, so the `{{variables}}` are checked too);
  `satisfies` fails the build when `fr` misses a key

# Testing translated components

```ts
// src/tests/setup.ts
import '../i18n';                      // the real instance, real English messages
```

```tsx
it('switches the title to French', async () => {
  render(<App />);
  await userEvent.selectOptions(screen.getByLabelText('Language'), 'fr');

  expect(screen.getByRole('heading', { name: 'Personnages de Star Wars' })).toBeInTheDocument();
});

afterEach(() => i18n.changeLanguage('en'));   // the instance is shared between tests
```

- Assert on the **text the user reads**, in a known language — don't mock `t`
- Reset the language after each test: i18next is a module-level singleton

# Recap

- **Format** with `Intl`: `NumberFormat` (currency, unit, compact), `DateTimeFormat`
  (`dateStyle`, time zone), `RelativeTimeFormat`, `PluralRules` — create formatters once
- **Translate** with i18next + react-i18next: resources per language, `fallbackLng`,
  `escapeValue: false`, `import './i18n'` once
- `useTranslation()` gives `t` and `i18n`; `i18n.changeLanguage()` re-renders the app;
  update `<html lang>`
- `{{name}}` interpolation, `count` + `_one` / `_other` plurals, `{{v, number}}` formatting,
  `<Trans>` for markup, ICU via a plugin
- `declare module 'i18next'` types the keys and the interpolation values

# Quiz — Question 1 / 3

**Which call displays a height in centimetres with the conventions of the user's locale, without any library?**

- **A.** `` `${height} cm` ``
- **B.** `new Intl.NumberFormat(locale, { style: 'unit', unit: 'centimeter' }).format(height)`
- **C.** `height.toFixed(0) + ' cm'`
- **D.** `new Intl.DateTimeFormat(locale).format(height)`

<v-click>

> ✅ **B** — `style: 'unit'` knows the units' symbols and long names in every locale, and
> applies the locale's digit grouping and decimal separator.

</v-click>

# Quiz — Question 2 / 3

**In French, `t('people', { count: 0 })` with only `people_one` and `people_other` defined returns…**

- **A.** "0 personnes"
- **B.** "0 personne"
- **C.** The key `people`
- **D.** An error: `people_zero` is required

<v-click>

> ✅ **B** — `Intl.PluralRules('fr').select(0)` is `"one"`: in French, zero takes the
> singular. That's why hand-written `count > 1` checks are wrong. Add `people_zero` for a
> dedicated "nothing" message.

</v-click>

---

# Quiz — Question 3 / 3

**Why set `interpolation: { escapeValue: false }` with react-i18next?**

- **A.** To allow HTML in translations
- **B.** Because React already escapes strings it renders — escaping twice would show `&lt;`
- **C.** It makes translations load faster
- **D.** It is required for plurals

<v-click>

> ✅ **B** — i18next escapes values by default for non-React uses. React escapes text
> content itself, so a second escape would display entities. It doesn't make HTML in
> messages render: that's what `<Trans>` is for.

</v-click>
