# 09 - Alerts, Timeline and Cases

---

# Learning objectives

At the end of this chapter, you will be able to:

- **Analyze** the alerts generated by the detection rules: triage, status, grouping
- **Correlate** the relevant data around an alert with **Timeline**
- **Track** security events and incidents with **Cases**

---

# The alerts table

* Every alert of every rule: **severity**, **risk score**, rule, host, user, reason
* **Group by** rule, host, user, source IP — 300 alerts become 4 groups
* **Status**: `open` → `acknowledged` → `closed` — with a **reason** when closing
  (*false positive*, *duplicate*, *true positive*…)
* **Assignees** and **tags**: who looks at what
* **Take action**: add to a case, add an exception, isolate the host, run a
  response action (Elastic Defend)

# Triage — the questions

<v-clicks>

1. **Is it real?** Read the reason, the source event, the investigation guide
2. **Is it known?** Prevalence, previous alerts, existing cases, exceptions
3. **How far?** Same user, same host, same IP — before and after
4. **How bad?** Asset criticality, privileges of the user, data at stake
5. **What now?** Close it (with a reason), escalate it to a case, contain the host

</v-clicks>

# Alerts are documents

* Stored in `.alerts-security.alerts-<space>` — query them like any index

```text
FROM .alerts-security.alerts-default
| WHERE kibana.alert.workflow_status == "open"
| STATS alerts = COUNT(*) BY kibana.alert.rule.name, host.name
| SORT alerts DESC
```

* ES|QL in Discover, dashboards on the alerts, rules on the alerts themselves
  (*"more than 5 high alerts on one host in 1h"*)

# Timeline

* An **investigation workspace**: drop events, alerts, queries — they stay together
* **Query** tab: KQL, EQL or ES|QL on the whole Security data view
* **Correlation** tab: an **EQL** query, its sequences displayed
* **Pinned events**: the evidence — kept whatever the query
* **Notes**: on the timeline, on each event
* **Drag and drop** any value from anywhere: a host, an IP, a hash → a filter

---

# From an alert to a timeline

<v-clicks>

1. **Investigate in timeline** on the alert — its source events are in
2. Add `host.name: ws-02` — the whole host, around the time
3. Sort by time — the **story** appears: `winword.exe` → `powershell.exe` → `updater.exe`
4. **Pin** each step, **note** what it means
5. Add the C2 IP — the beacon, every minute, and the exfiltration
6. **Save** the timeline — it is the investigation's record

</v-clicks>

---

# Timeline templates

* A **template** = a saved query with **placeholders**: `host.name: {host.name}`
* Attached to a rule: *Investigate in timeline* fills them from the alert
* One template per kind of investigation: *Process tree of a host*,
  *Authentications of a user*, *Flows of an IP*
* Prebuilt templates: *Generic Endpoint*, *Generic Network*, *Generic Process*

---

# Cases

* A **case** = an incident: a title, a description, a **severity**, a **status**
  (`open` → `in progress` → `closed`), **assignees**, **tags**
* **Attach** alerts, timelines, Lens visualizations, files, observables
* **Comments** and **activity**: who did what, when
* **Custom fields** and **templates**: the fields of your process
* **Connectors**: push the case to **Jira**, **ServiceNow**, IBM Resilient,
  Swimlane, TheHive, a webhook

# The incident workflow

```text
 Rule        Alert         Triage        Case           Response       Close
┌──────┐   ┌───────┐   ┌──────────┐   ┌────────┐   ┌──────────────┐   ┌──────┐
│ EQL  │──▶│ open  │──▶│ timeline │──▶│ in     │──▶│ isolate host │──▶│ root │
│ rule │   │       │   │ pivots   │   │progress│   │ reset creds  │   │ cause│
└──────┘   └───────┘   └──────────┘   └────────┘   └──────────────┘   └──────┘
                                           │
                                           ▼
                                    Jira / ServiceNow
```

* **Close the loop**: every closed case improves a rule, an exception or a dashboard
